complete reference

103 names, 13 clusters, one job

Prompt, context, harness, loop, and graph engineering (see the 5-era flow) are the trunk. Everything else people call "___ engineering" or "___ agents" this year is a branch off one of those five. This page groups the other 98 terms into 13 clusters, researched and cited where a real origin exists — and labeled as generic industry jargon where it doesn't.

01

the input layer

01Prompt, instruction & system-prompt engineering

P C H L

Mostly a Prompt-era concern

Before any of the other twelve clusters exist, someone has to write down what the model should do. This is the direct descendant of the prompt engineering era — split into narrower specialties as teams needed to separate the one-time system rules from the per-turn instructions, and to guarantee the shape of what comes back out.

Prompt Engineering
Crafting and iterating on the wording, examples, and formatting sent to a model to reliably get the output you want. No single coiner — it emerged organically around GPT-3 (2020–21) as practitioners found phrasing alone shifted quality.
Instruction Engineering
Writing just the task directive itself — the "do X" — as distinct from the examples, persona, or formatting around it. Informal industry usage, generally treated as a subset of prompt engineering rather than its own discipline.
System Prompt Engineering
Designing the persistent, session-wide rules (persona, tone, guardrails) set once at the API's "system" role instead of repeated every turn. The "system" role is an OpenAI Chat Completions convention from 2023; the practice around it is generic industry usage.
Structured Outputs
Forcing a model's response to strictly match a schema, usually JSON, instead of free text. Real origin: OpenAI's Structured Outputs launch, Aug 2024, which guaranteed 100% schema adherence.
02

the frame, extended

02Context & memory engineering

P C H L

Mostly a Context-era concern

This is the context engineering era broken into the specific jobs a real system has to do: deciding what to pull in, how to compress or cache it, when to drop it, and — once a session ends — what an agent is allowed to remember next time.

Context Engineering
Curating the entire set of tokens the model sees — not just the prompt, but retrieved docs, tool output, and history. Coined by Shopify's Tobi Lütke (June 2025); formalized by Anthropic's "Effective context engineering for AI agents," Sept 2025.
Context Orchestration
Coordinating which context-producing subsystems — retrieval, memory, tools — fire, in what order, for a given turn. Generic industry phrase; about runtime sequencing rather than curation strategy.
Context Routing
Deciding which context source or variant — which knowledge base, which memory partition — to send for a given query. Generic connector-word phrasing, no single origin.
Context Management
The operational lifecycle of what's inside the window: adding, expiring, and budgeting tokens across a session. Generic term, framed around window constraints rather than source coordination.
Context Compression
Shrinking context via summarization or extraction to fit a token budget while preserving meaning. Umbrella term; specific techniques (Microsoft's LLMLingua line) are named, the umbrella itself isn't.
Context Caching
Reusing previously-computed context — a KV-cache/prefix — across calls instead of resending it. Real origin: Anthropic's prompt caching launch, Dec 2024 (up to 90% cost, 85% latency reduction).
Context Pruning
Actively removing stale or low-relevance items from context mid-session, as opposed to compressing everything uniformly. Generic research/industry phrasing.
Context Retrieval
Fetching external context to insert into the prompt — the "R" step of RAG, reframed as a context-engineering concern rather than a retrieval-systems one.
Context Assembly
The final, concrete step of composing instructions, retrieved content, memory, and history into the actual token sequence sent to the model.
Memory Engineering
Designing the storage, write/update policy, and consolidation systems that let an agent persist and recall information across turns. Commonly grounded in Sumers et al., "Cognitive Architectures for Language Agents" (CoALA), 2023.
Memory Management
The operational lifecycle of stored memories — writing, updating, expiring, deduplicating — the day-to-day counterpart to Memory Engineering's design work.
Long-Term Memory
Information persisted across sessions, e.g. in a vector store, that survives beyond the current context window. Borrowed from cognitive psychology's classic memory-systems model.
Short-Term Memory
In agent terms, the active context window / scratchpad for the current session — available "in-mind" for the task but not persisted afterward. CoALA calls this "working memory."
Semantic Memory
Stored facts and general world knowledge an agent can draw on, not tied to a specific past event. Traces to Endel Tulving's 1972 semantic/episodic distinction, adopted directly by CoALA.
Episodic Memory
A log of specific past experiences, preserved with their original context rather than abstracted into general facts. Same Tulving 1972 lineage; the difference from semantic memory is instance-specific record vs. generalized fact.
03

beyond the window

03Retrieval, knowledge & search engineering

P C H L

Context-era, with Harness (tools call retrieval)

Once context has to come from somewhere, you need a retrieval stack. This cluster runs from the foundational RAG paper through its agentic and graph-based descendants, plus the older discipline — knowledge engineering — that RAG borrowed its whole premise from.

Retrieval Engineering
The umbrella practice of building the retrieval stack that feeds an LLM — chunking, embedding, indexing, ranking — independent of any one source. Parent discipline for RAG Engineering and its variants.
RAG Engineering
The applied, production-focused practice of building and operating retrieval-augmented generation pipelines. Builds on Lewis et al., "Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks," NeurIPS 2020.
Agentic RAG
RAG where an autonomous agent, not a fixed pipeline, decides when and whether to retrieve, and can iterate or use multiple tools mid-task. Formalized in Singh et al., "Agentic Retrieval-Augmented Generation," Jan 2025.
Graph RAG
Retrieving from a knowledge graph of entities and relationships instead of flat vector similarity, for questions that need connected reasoning across a corpus. Origin: Microsoft Research's GraphRAG, April 2024.
Adaptive RAG
Dynamically choosing a retrieval strategy — none, single-step, or multi-step — per query via a complexity classifier. Origin: Jeong et al., "Adaptive-RAG," NAACL 2024.
Knowledge Engineering
Predates LLMs entirely — the classic AI discipline of structuring expert knowledge into ontologies and rule bases, rooted in 1970s–80s expert systems (Dendral, MYCIN). Modern use: building the ontologies/graphs that feed Graph RAG.
Agentic Search
An agent iteratively planning, running, and refining multiple search queries against live sources until it has enough information, rather than one keyword lookup. Vendor-popularized term, no single paper.
Deep Research
A shipped, named capability where an agent autonomously browses and synthesizes findings into a long-form report. Origin: OpenAI's "Introducing deep research," Feb 2025, followed by Gemini and others.

the engine, disassembled

04Harness, scaffolding & runtime engineering

P C H L

Mostly a Harness-era concern

This is the harness engineering era taken apart into its layers: the harness itself (model + tool wiring), the older "scaffolding" vocabulary it grew out of, and the production runtime and infrastructure that host many harnesses at once.

Harness Engineering
Building and continuously hardening the system around a model — tools, guardrails, permanent fixes for recurring mistakes — so it operates reliably. Coined by Mitchell Hashimoto in "My AI Adoption Journey," Feb 2026; later formalized on Martin Fowler's site.
Agent Harnesses
The concrete software layer wrapping a model: manages the API connection, dispatches tool calls, controls what fits in context. Shorthand — "Agent = Model + Harness" — per LangChain's "Anatomy of an Agent Harness".
Agent Scaffolding
The older, AI-safety/eval-community term — predates "harness," used for systems like AutoGPT — for the control loop and action-handling code around an LLM. No single coiner.
Scaffold Engineering
Not an independently established discipline. Shows up as a variant of the scaffolding vocabulary, paralleling "harness engineering" without its own distinct literature.
Agent Runtime Engineering
The engineering discipline behind building and operating an agent runtime (below) — analogous to site reliability engineering, but for agents.
Agent Runtime
The production hosting/execution layer that runs an agent's control loop at scale: invoking the model, executing tool calls, persisting state, and enforcing security boundaries across many sessions.
Agent Infrastructure
The widest term in this cluster: the full stack — compute, retrieval, tooling, observability, governance — that runtimes and harnesses sit on top of.
Cognitive Architecture
Rooted in classical symbolic AI (Soar, ACT-R) decades before LLMs — models reasoning via distinct memory and control systems. Modern reuse: CoALA, Sumers et al. 2023, applying the same split to language agents.
05

reaching outside the model

05Tools & protocol engineering

P C H L

Mostly a Harness-era concern

A harness is only as capable as what it can call. This cluster covers how a model actually invokes something outside itself — from the vendor API that made it standard, to the open protocol that now lets any agent talk to any tool server.

Tool Engineering
The practice of designing tool schemas and descriptions so a model calls them correctly. No canonical origin — an emerging counterpart to prompt engineering, focused on interfaces rather than wording.
Tool Use
The general capability of an LLM invoking external functions mid-reasoning. Broader than Function Calling — studied academically (Toolformer, ReAct) independent of any vendor API; key origin Yao et al., "ReAct," 2022.
Function Calling
The specific vendor API feature where a model outputs JSON matching a developer schema to request an action. Origin: OpenAI, June 2023.
Tool Routing
The decision logic that selects which tool, among many available, to invoke for a given step — a sub-problem of orchestration focused on the "which" choice.
Tool Orchestration
Broader than routing: the end-to-end sequencing, chaining, and error-handling of multiple tool calls within a task.
MCP / Model Context Protocol
An open protocol standardizing how AI apps connect to external data and tools via a client-server architecture. Origin: Anthropic, Nov 2024. Distinct from function calling: MCP standardizes discovery and transport across many tool servers, not one model's call mechanism.
06

more than one agent

06Orchestration & multi-agent systems

P C H L G

Harness-era, spilling into Loop and Graph

Once you have more than one moving part — multiple agents, multiple models, or packaged capabilities that need dispatching — someone has to coordinate them. This cluster covers that coordination layer, plus the two open protocols and the "compound systems" framing that made multi-part AI applications a distinct architecture.

Agent Orchestration
Coordinating one or more agents' steps, state, and control flow to complete a task. Most often used for multi-agent coordination specifically.
Multi-Agent Orchestration
The specific case of two or more distinct agents coordinating — sequential handoff, parallel fan-out, hierarchical delegation.
Model Orchestration
Coordinating calls across multiple models — routing a query to different LLMs, chaining model calls with non-model steps. The unit coordinated is the model call, not an autonomous agent.
Model Routing
Selecting which model to send a given request to, by cost, latency, or task type — narrower than orchestration.
Skill Routing
Selecting which packaged Skill to invoke for a task, distinct from tool/model routing by unit — a Skill bundles instructions and resources, not a single function.
Skills
Modular, reusable folders of instructions, scripts, and resources an agent can load on demand for a specialized task. Announced by Anthropic, Oct 2025, released as a cross-vendor open standard in Dec 2025.
Sub-agents
A named, isolated agent instance a parent spawns to handle a bounded subtask and returns only a final result, keeping the parent's context clean. Documented in Claude Code's sub-agent docs.
Agent Delegation
The behavior of one agent handing a task to another — sub-agents are one implementation of it; delegation is the decision itself.
A2A / Agent-to-Agent
An open protocol letting agents built by different vendors discover each other's capabilities and coordinate as peers, via Agent Cards. Origin: Google, April 2025; contributed to the Linux Foundation, June 2025. MCP connects an agent to tools; A2A connects agents to each other.
Compound AI Systems
Systems where the best-performing application isn't one big model but multiple components — retrievers, verifiers, smaller models — working together. Coined in Berkeley BAIR's "The Shift from Models to Compound AI Systems," Feb 2024.
Compound Agents
An informal narrowing of Compound AI Systems to cases where the components are themselves autonomous, tool-using agents. No distinct canonical source of its own.
Graph Engineering
Organizing multiple agents, loops, tools, and evaluators into an explicit graph — nodes as work units, edges as handoffs (including conditional and rollback paths), a shared state all nodes read/write, and routing rules that decide what runs next — instead of leaving that control flow implicit inside one agent's context. A generalization of workflow engineering: a workflow node is a fixed function, a graph node can be a full agent that loops, uses tools, and retries on its own. The name went viral in July 2026, but the practice predates it — see Anthropic's Building Effective Agents (Dec 2024) and LangGraph (open-sourced 2024).
07

thinking before acting

07Planning & reasoning

P C H L

Harness-era, spilling into Loop

The step between "goal received" and "first action taken." This cluster covers how an agent breaks a goal into steps, and the family of "reasoning model" techniques — spending more compute at inference time — that made multi-step thinking a first-class capability rather than a prompting trick.

Agent Planning
An agent formulating a sequence of steps or subgoals before or while acting, rather than answering in one shot. Draws on classical AI planning (STRIPS-era) repurposed for LLM agents.
Agentic Planning
Near-synonymous with Agent Planning, but tends to describe planning as an explicit architectural module — a planner LLM plus an executor LLM — inside a broader multi-agent system.
Task Decomposition
Breaking a compound goal into smaller subtasks that can be solved independently. Real academic lineage: Hierarchical Task Network planning, Erol et al. 1994.
Reasoning Systems
The broadest term here — any architecture whose core value is multi-step inference (chain-of-thought, tree-of-thought, tool-augmented reasoning, "reasoning models" like o1). Test-Time Compute and ReAct are specific instances of it.
Test-Time Compute
Spending extra computation at inference time — longer chains of thought, sampling multiple candidates, verification — instead of only at training time. Popularized by OpenAI's o1 (Sept 2024); grounded in Snell et al., "Scaling LLM Test-Time Compute Optimally," 2024.
Inference-Time Scaling
Largely a synonym for Test-Time Compute, used more when discussing the empirical scaling curves — how quality improves as inference compute increases.
Cognitive Loops
An informal term for the repeated perceive-think-act cycle an agent runs, echoing classical cognitive-architecture language (Soar, ACT-R). Broader and softer than ReAct — ReAct is one specific named implementation of this loop shape.
ReAct Loops
The specific "reason + act" pattern where a model alternates generating a thought and taking an action, observing the result, and repeating. Origin: Yao et al., "ReAct," 2022 — the direct ancestor of most modern tool-using agent loops.
08

the routine, disassembled

08Loops, reflection & verification

P C H L

Mostly a Loop-era concern

This is the loop engineering era split into its actual mechanisms: loops built around self-critique, loops built around an external correctness check, and the question of which party — human or model — sits inside the loop doing the checking.

Loop Engineering
Designing an agent's repeated control cycle — generate, check, revise, act — as a deliberate engineering artifact, not an incidental prompt chain. Umbrella term for this cluster.
Reflection Loops
A loop built around a model critiquing its own output and feeding that critique back in to improve the next attempt. Operationalized in Madaan et al., "Self-Refine," 2023.
Verification Loops
A loop where each step or final output is checked against an explicit correctness signal — unit tests, a verifier model, execution feedback — before it's accepted or retried. Grounded in Lightman et al., "Let's Verify Step by Step," 2023.
Self-Reflection
A model generating natural-language critique of its own prior output or trajectory, stored and reused. Canonical origin: Shinn et al., "Reflexion," NeurIPS 2023.
Self-Correction
A model revising its own output after detecting an error — with a caveat: Huang et al., 2023 found intrinsic self-correction, without external feedback, often fails or hurts performance.
Self-Verification
Narrower than self-correction: checking whether an answer is correct without necessarily fixing it, often used to select among sampled candidates (best-of-N with a verifier).
Human-in-the-Loop
A workflow where a human reviews, approves, or corrects outputs at one or more points, rather than fully autonomous operation. Traces to cybernetics and control theory (Norbert Wiener, 1940s).
Model-in-the-Loop
The mirror image: a smaller or specialized model sits inside a workflow to check, filter, or flag a human's or another model's output for review.
09

does it actually work

09Evaluation & reliability engineering

P C H L

Loop-era, cross-cutting into Harness

Every other cluster on this page eventually has to answer to this one. Evals decide whether a change made things better or worse; reliability and safety engineering decide whether a system is fit to run unattended; observability decides whether anyone can tell what happened when it didn't.

Evaluation Engineering
Designing and maintaining the test harnesses, datasets, and scoring pipelines used to measure LLM/agent quality as a versioned, CI-integrated artifact rather than an ad hoc notebook.
Evals Engineering
Effectively a synonym, using the more colloquial "evals" shorthand cemented by OpenAI's open-source evals framework, 2023.
Automated Evals
Running evaluation checks programmatically — scripted assertions, unit tests, regression suites — without a human scoring each output by hand. LLM-as-a-Judge is one technique within this category, not a synonym for it.
LLM-as-a-Judge
Using a strong LLM to score or compare other models' outputs in place of human raters. Origin: Zheng et al., "Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena," NeurIPS 2023 — found ~85% agreement with humans, exceeding human-human agreement.
Agent Benchmarks
Standardized task suites measuring end-to-end agent capability — tool use, multi-step execution — rather than single-turn text quality. Concrete examples: SWE-bench, GAIA, AgentBench.
Reliability Engineering for Agents
Applying SRE-style discipline — uptime, failure-mode analysis, retries, monitoring — to agent systems, whose failure modes (looping, tool misuse) differ from ordinary software.
AI Reliability Engineering
Broader than the agent-specific version: the general reliability, consistency, and reproducibility of any AI system in production, agentic or not.
AI Safety Engineering
Preventing harmful or misaligned behavior specifically — red-teaming, refusal behavior, guardrails — as distinct from reliability's focus on uptime. Draws on the broader AI safety research field.
Agent Observability
Instrumenting agents with traces, spans, and tool-call logs so engineers can see why an action was taken or where it failed. Emerging standard: OpenTelemetry's GenAI semantic conventions.

what it's allowed to touch

10Governance & sandboxing

P C H L

Mostly a Harness-era concern

As agents got real tool access — shells, browsers, production data — a security-shaped layer had to exist alongside the harness: content-level constraints, execution isolation, access control, and the organizational policy sitting above all three.

Guardrails
Programmatic checks — input/output filters, policy rules, content classifiers — placed between a user/app and an LLM to constrain what it can say or do. Popularized by NVIDIA's NeMo Guardrails, 2023.
Agent Sandboxing
Running an agent's code execution, shell, or browser actions inside an isolated environment (container, microVM) so a mistake can't touch the host system. Distinct from guardrails: an infrastructure boundary, not a content filter.
Agent Permissions
The access-control layer defining which tools, data scopes, and actions a given agent is allowed to invoke — typically least-privilege, applied per task.
Agent Governance
The organizational policy, oversight, and auditing layer for how agents are approved and monitored across an enterprise — the "who decides" layer above permissions and sandboxes.
11

running it at scale

11Ops & systems engineering

P C H L G

Spans all five eras at once

The odd one out — this cluster doesn't map onto a single era because it's the discipline of running all five eras in production at once: deployment, monitoring, governance, and the serving-layer economics of every call the other clusters make.

LLMOps
The operational discipline — deployment, prompt/version management, monitoring — for running LLM-powered applications in production. Explicitly framed by practitioners as "MLOps for LLMs."
AgentOps
Extends LLMOps to handle multi-step agent behavior — tool calls, long time horizons, multi-agent interaction — rather than a single prompt/response.
ModelOps
A broader, Gartner-defined discipline covering governance and lifecycle management of all operationalized AI/decision models, not just LLMs — model-type-agnostic and compliance-driven.
AI Engineering
Building applications on top of pre-trained foundation models — via APIs, prompting, RAG, fine-tuning — rather than training models from scratch. Popularized as a distinct discipline by Chip Huyen's "AI Engineering," 2025.
AI Systems Engineering
A broader, infrastructure-oriented framing: the end-to-end system — data pipelines, serving infra, monitoring — surrounding a model in production.
Agentic Systems Engineering
Systems engineering applied specifically to multi-step, tool-using agents — the orchestration and state management that let agents run reliably over long horizons.
AI Application Engineering
Building the user-facing product layer — UX, business logic, integration — around AI capabilities, as distinct from the model-serving or infra layer.
Inference Engineering
Serving trained models to users at scale — optimizing latency, cost, and throughput via quantization, batching, and cache management — distinct from training or prompting, which shape what a model says rather than how fast it runs.
Forward Engineering
Not a standard AI/ML term. In its actual usage (data modeling) it means translating a designed model into an implemented system — the opposite of reverse engineering. Rarely used in an AI context; included here because it appears on lists like this one.

what gets built

12Agent archetypes & workflows

P C H L

Harness-era, spilling into Loop

The shapes agents actually take once harness, tools, and loop are in place — from the four workflow patterns that first made "agentic" a household word, to the specific archetypes (coding, computer-use, deep) that now have their own tooling.

Agent Engineering
The practical discipline of designing and tuning an individual agent — its prompts, tools, memory, control loop. Agent-level, not system-level.
Agentic Engineering
A broader framing than Agent Engineering — building agentic systems, orchestration, and delegation between sub-agents, rather than one agent's internals. The two terms are used somewhat interchangeably in practice.
Agentic Workflows
Multi-step processes where output is generated iteratively through defined patterns — reflection, tool use, planning, multi-agent collaboration. Popularized as an umbrella term by Andrew Ng, March 2024.
Workflow Engineering
Designing the explicit control-flow layer — steps, branches, handoffs — that structures how agentic systems execute, one abstraction level above a single prompt.
Autonomous Agents
Systems that pursue a goal through multiple steps with minimal human intervention per step. Predates the current LLM-agent wave as a term from classic AI/robotics literature.
Deep Agents
Harnesses built for long-horizon tasks — deep research, complex coding — combining explicit planning, persistent file-system memory, and sub-agent spawning. Popularized by LangChain, 2025.
Computer-Use Agents
Agents that control a computer through its actual GUI — mouse, keyboard, screenshots — rather than through APIs. Origin: Anthropic's Computer Use, Oct 2024.
Coding Agents
Agents scoped to software-engineering tasks — planning, editing across files, running tests — via a code/terminal interface rather than GUI control. Defined by early exemplars like Cognition's Devin and the academic SWE-agent project.

how people actually work now

13Emerging practice & culture

P C H L

Prompt-era practice, Harness-era discipline

The newest cluster on this page, and the least settled — names for how the day-to-day habit of writing software is visibly changing, from the viral tweet that named the loose end of the spectrum to the more disciplined methodology built as a direct reaction to it.

Vibe Coding
Coding by describing intent in natural language and accepting AI-generated code largely without reading it line-by-line. Origin: Andrej Karpathy, Feb 2025 — later named Collins Dictionary's 2025 Word of the Year.
Spec-Driven Development
Structuring AI-assisted coding around a written specification first, broken into small testable tasks an agent then implements — a deliberate reaction to vibe coding's lack of rigor for production work. Origins: GitHub's Spec Kit and AWS's Kiro, both 2025.
AI-Native Development
Building software with AI embedded as a core architectural element from the outset, rather than bolted onto an existing workflow. Broader philosophy than any single methodology.
AI-Native Software Engineering
The engineering-discipline framing of the same idea — applying "AI as architectural core" to the professional practice, review, and accountability structures of software engineering specifically. Used near-interchangeably with AI-Native Development.

The bottom line

Almost none of these 103 names describe a new idea. Most describe an old idea — planning, memory, verification, access control — meeting a model that can call tools and run in a loop. Prompt, context, harness, loop, and graph are still the only five layers you actually have to build. Everything on this page is either a part of one of those five, or the discipline of operating them all at once.
